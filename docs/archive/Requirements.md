Нужно спроектировать и реализовать MVP desktop-приложения для macOS, которое записывает две отдельные аудиодорожки во время онлайн-митингов:
1) микрофон пользователя
2) системное аудио - все, что пользователь слышит в наушниках / на выходе системы

Сначала проанализируй задачу и предложи краткий план реализации, затем переходи к коду.

Контекст
- Платформа: macOS, целевая версия - Ventura или новее
- Язык: Swift
- UI: SwiftUI
- Захват микрофона: AVAudioEngine
- Захват системного аудио: ScreenCaptureKit
- Конвертация в MP3: через ffmpeg или LAME, вызываемый как subprocess
- Приложение локальное, без серверной части
- Целевой сценарий: ручная запись онлайн-митингов с сохранением исходных дорожек для последующей расшифровки

Цель
Реализовать MVP desktop-приложения для macOS, которое:
- по нажатию Start Recording начинает одновременную запись микрофона и системного аудио
- сохраняет оригинальные дорожки в несжатом формате PCM
- по нажатию Stop Recording завершает запись, сохраняет исходники и конвертирует каждую дорожку в MP3
- сохраняет метаданные сессии записи
- после завершения открывает папку с результатами

Scope
Включено в MVP
- локальное приложение для одного пользователя
- ручной запуск и остановка записи
- запись в реальном времени
- сохранение файлов на диск
- отдельные дорожки mic и system
- пост-обработка с конвертацией WAV/CAF -> MP3
- базовая обработка ошибок и статусы UI

Не включено в MVP
- транскрибация
- интеграции с Zoom / Teams / Google Meet API
- облачная синхронизация
- multi-user
- speaker diarization
- горячие клавиши
- автостарт по событию
- объединение дорожек в один файл

Функциональные требования

1. Управление записью
- В UI должны быть:
  - кнопка Start Recording
  - кнопка Stop Recording
  - статус приложения:
    - idle
    - recording
    - processing
- Состояния должны быть явно видны пользователю
- Запуск и остановка должны работать вручную

2. Захват аудио
- Нужно записывать:
  - микрофон с выбранного input-устройства
  - системное аудио - все, что воспроизводится в системе
- Два потока должны писаться одновременно
- Требуется синхронный старт потоков с минимально возможной погрешностью
- Нужно предусмотреть best effort поддержку:
  - встроенного микрофона
  - внешних микрофонов
  - Bluetooth-гарнитур

3. Формирование дорожек
- Создавать отдельные файлы:
  - mic.wav или mic.caf
  - system.wav или system.caf
- Формат внутренней записи: PCM без сжатия
- Нормализовать или явно зафиксировать:
  - sample rate
  - channels
- Важно обеспечить максимально близкую длительность дорожек

4. Сохранение результатов
- Для каждой записи создавать отдельную папку вида:
  - /Recordings/YYYY-MM-DD-HHMM/
- Внутри сохранять:
  - исходную дорожку микрофона
  - исходную дорожку системного аудио
  - MP3-версии обеих дорожек
  - metadata.json

5. Конвертация
- После Stop Recording:
  - завершить запись
  - сохранить исходные PCM-файлы
  - сконвертировать каждую дорожку в MP3
- Итоговые файлы:
  - mic.mp3
  - system.mp3
- Исходники не удалять

6. Метаданные
- Сформировать metadata.json со следующими полями:
  - timestamp начала записи
  - timestamp окончания записи
  - длительность
  - использованные устройства
  - sample rate
  - channels
  - пути к итоговым файлам
  - статус post-processing
  - ошибки, если были

Нефункциональные требования

1. Производительность
- Старт записи - менее 1 секунды
- Во время записи не должно быть drop frames / audible gaps, если это возможно в рамках платформенных ограничений
- Не делать лишние CPU-heavy операции в real-time capture path

2. Надежность
- При ручной остановке запись должна корректно завершаться
- При аварийном завершении приложения - best effort flush буферов и сохранение уже записанных данных
- Если MP3-конвертация не удалась, WAV/CAF должны остаться сохраненными

3. Качество аудио
- Без сжатия на этапе записи
- Без искусственной обработки сигнала
- Избегать clipping
- Корректно обрабатывать разные sample rate устройств

4. UX
- Минималистичный интерфейс
- Не более 1-2 экранов
- Понятные статусы
- Понятные ошибки с actionable сообщением

Технические требования

Архитектура
Раздели решение на компоненты:
1) UI Layer
2) Recording Manager
3) Mic Capture Module
4) System Audio Capture Module
5) Audio Sync / Buffer Layer
6) File Writer
7) MP3 Encoding Module
8) Metadata Writer
9) Permissions Manager
10) Error Handling / Logging

Требования к реализации
- Используй SwiftUI для UI
- Сделай архитектуру достаточно модульной, чтобы в будущем можно было добавить:
  - выбор устройств
  - индикатор уровня сигнала
  - объединение дорожек
  - транскрибацию
- Раздели real-time capture и post-processing
- Не смешивай UI-логику и low-level audio capture
- Добавь понятные модели состояния записи

Обработка разрешений
Приложение должно корректно работать с системными permission flows:
- Microphone access
- Screen Recording / System Audio Recording, если требуется платформой для ScreenCaptureKit
Если разрешения отсутствуют:
- показать понятную ошибку
- объяснить, что нужно включить
- предложить открыть System Settings, если это возможно

Обработка ошибок
Нужно явно обработать сценарии:
1) Нет доступа к микрофону
2) Нет доступа к захвату system audio
3) Устройство отключено во время записи
4) Ошибка создания файлов / папки
5) Ошибка MP3-кодирования
6) Ошибка инициализации ScreenCaptureKit / AVAudioEngine
7) Несовпадение форматов потоков

Поведение при ошибках
- Не падать без необходимости
- Если один поток недоступен, по возможности явно сообщить и продолжить запись доступного потока только если это безопасно и не ломает UX
- Все ошибки логировать
- WAV/CAF сохранять даже если MP3-конвертация не удалась

Основной user flow
1) Пользователь запускает приложение
2) Видит статус idle
3) Нажимает Start Recording
4) Приложение проверяет permissions
5) Приложение начинает запись mic + system audio
6) Пользователь участвует в митинге
7) Пользователь нажимает Stop Recording
8) Приложение завершает запись и переходит в processing
9) Сохраняются исходные дорожки
10) Выполняется конвертация в MP3
11) Генерируется metadata.json
12) Открывается папка с результатами
13) Статус возвращается в idle или completed, если введешь дополнительное состояние

Acceptance criteria
Считай задачу выполненной, если:
1) По нажатию Start начинается запись двух потоков - mic и system
2) По нажатию Stop формируются 2 отдельных PCM-файла
3) После post-processing формируются 2 MP3-файла
4) Оба исходных файла воспроизводятся корректно
5) Оба MP3-файла воспроизводятся корректно
6) Длительности дорожек совпадают в пределах допустимой погрешности
7) Нет явных audible артефактов при типовом сценарии записи митинга
8) metadata.json содержит ключевые параметры сессии
9) При отсутствии разрешений пользователь получает понятную ошибку
10) При ошибке MP3-конвертации исходники не теряются

Ограничения
- Не добавляй серверную часть
- Не добавляй интеграции с внешними meeting platforms
- Не реализуй транскрибацию в MVP
- Не делай избыточно сложный UI
- Минимизируй количество зависимостей
- Не обновляй системные или сторонние зависимости без явной необходимости
- Не делай массового рефакторинга вне задачи

Открытые вопросы, которые пока можно зафиксировать как разумные дефолты для MVP
Если эти параметры не заданы явно, прими следующие дефолты:
- MP3 bitrate: 192 kbps
- Channels: сохранять нативно или приводить к предсказуемому формату, если это упрощает стабильность
- UI выбора input/output устройств: не обязателен для первого MVP, но архитектурно заложи возможность добавить позже
- Realtime level meter: не обязателен
- Автоудаление старых записей: не реализовывать
- Логирование: локальный файл логов + console logs в debug
